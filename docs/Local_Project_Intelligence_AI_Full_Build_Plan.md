# Local Project Intelligence AI — Full Build Plan

## 1. Project Goal

Build a fully local AI system that can understand a large enterprise codebase and answer difficult technical questions as if it were a technical lead who has studied the project.

The system must support:

- Java
- SQL
- Java + SQL projects
- Java + Spark + SQL projects
- Large repositories
- Static code analysis
- Dynamic SQL reconstruction
- Metadata-driven SQL generation
- Cross-file dependency analysis
- Project architecture understanding
- Code search
- SQL/data-flow tracing
- Impact analysis
- Root-cause investigation
- Technical explanations
- Optional Git/history analysis
- Local LLM inference
- Web UI

### Primary target project

Start with:

- Approximately 2,000 files
- Approximately 70 MB
- Java + SQL

After the architecture is proven, support the second:

- Java + Spark + SQL

The application must be designed so the indexing and intelligence layer is reusable across both projects.

---

# 2. Core Principle

Do NOT build this as a simple:

```text
Code -> chunks -> embeddings -> vector database -> LLM
```

That architecture is insufficient for difficult enterprise-code questions.

The system must combine:

```text
Java AST analysis
+
SQL parsing
+
Symbol indexing
+
Call/reference analysis
+
Dynamic SQL analysis
+
Metadata-flow analysis
+
Dependency graph
+
Semantic/vector retrieval
+
Keyword search
+
Optional runtime evidence
+
LLM reasoning
```

The LLM is the reasoning layer.

The project index is the long-term project memory.

The graph represents relationships.

Retrieval finds relevant context.

Static analysis reconstructs deterministic relationships.

The LLM must not be expected to infer the entire project from embeddings alone.

# 5. Most Important Capability: Dynamic SQL Understanding

This is a first-class requirement.

The codebase may construct SQL in many different ways.

The system must recognize at least the following patterns.

## Pattern A — SQL from constants

Example:

```java
private static final String SQL =
    "SELECT A, B FROM CUSTOMER WHERE STATUS = ?";
```

The indexer must identify:

```text
Java class
  |
  +-- constant: SQL
        |
        +-- SQL query
             |
             +-- table: CUSTOMER
             +-- columns: A, B
             +-- filter: STATUS
```

---

# 6. Pattern B — SQL stored in a constants class

Example:

```java
String sql = QueryConstants.GET_CUSTOMER;
```

The system must follow:

```text
Current method
    |
    +-- references QueryConstants.GET_CUSTOMER
                         |
                         +-- actual SQL
```

The SQL parser then analyzes the resolved SQL.

---

# 7. Pattern C — Table name obtained from metadata using constant SQL

Example conceptual flow:

```java
String table = getTableName(Constants.GET_TABLE_SQL);
```

The system must understand:

```text
Constant SQL
     |
     v
Metadata query
     |
     v
Metadata table
     |
     v
Returned table name
     |
     v
Dynamic SQL
```

For example:

```text
Java method
   |
   +--> Constants.TABLE_LOOKUP_SQL
             |
             +--> queries metadata table
                       |
                       +--> returns physical/logical table name
                                      |
                                      +--> used by generated SQL
```

The actual organization-specific names must remain inside the user's environment.

---

# 8. Pattern D — Columns obtained from another metadata table

Example conceptual flow:

```text
1. Query metadata table A
      -> determine table

2. Query metadata table B
      -> determine columns

3. Construct SQL

SELECT <dynamic columns>
FROM <dynamic table>
WHERE ...
```

The system must preserve this chain.

Example internal representation:

```text
MetadataLookup
    |
    +-- lookup_type = TABLE
    +-- source = MetadataTableA
    +-- lookup_key = CONSTANT_X
    +-- result = TableName

MetadataLookup
    |
    +-- lookup_type = COLUMN
    +-- source = MetadataTableB
    +-- lookup_key = CONSTANT_Y
    +-- result = ColumnList

DynamicSQL
    |
    +-- table_source = MetadataLookup[TableName]
    +-- column_source = MetadataLookup[ColumnList]
```

This is significantly more important than ordinary semantic similarity search.

---

# 9. Pattern E — SQL assembled from variables

Example:

```java
String sql = SELECT + columns + FROM + table + WHERE + condition;
```

The system must build an expression graph:

```text
sql
 |
 +-- SELECT
 +-- columns
 |     |
 |     +-- metadata lookup
 |
 +-- FROM
 |     |
 |     +-- metadata lookup
 |
 +-- WHERE
       |
       +-- variable
```

The final query may not be statically knowable.

The system must therefore distinguish:

```text
RESOLVED
PARTIALLY_RESOLVED
UNRESOLVED
```

It must never invent a table or column.

---

# 10. Pattern F — String concatenation

Recognize:

```java
String sql = "SELECT " + column + " FROM " + table;
```

Track the origin of:

- SQL fragments
- variables
- method return values
- constants
- configuration
- metadata results

---

# 11. Pattern G — StringBuilder

Recognize:

```java
StringBuilder sql = new StringBuilder();

sql.append("SELECT ");
sql.append(columns);
sql.append(" FROM ");
sql.append(table);
```

The analyzer must reconstruct the expression where possible.

---

# 12. Pattern H — Method-generated SQL

Example:

```java
String sql = queryBuilder.buildQuery(metadata);
```

The system must follow:

```text
caller
  |
  +--> queryBuilder.buildQuery()
              |
              +--> metadata
              |
              +--> SQL construction
```

If the method is too complex for static resolution, mark it as partially resolved and provide the evidence.

---

# 13. Pattern I — SQL generated through multiple methods

Example:

```text
methodA()
   |
   +--> methodB()
           |
           +--> getMetadata()
           |
           +--> buildTableName()
           |
           +--> buildColumnList()
           |
           +--> buildSQL()
```

The agent should be able to trace this chain.

---

# 14. Pattern J — SQL generated from configuration

Recognize SQL/table/column information coming from:

- properties files
- YAML
- XML
- JSON
- environment/configuration files
- Java constants
- configuration classes

The source of every resolved value should be recorded.

# 15. Pattern K — SQL templates

Recognize patterns such as:

```text

+
runtime variables
+
metadata

final SQL
```

Represent the template separately from runtime values.

# 22. Metadata-Driven SQL Flow

Represent metadata-driven logic explicitly.

Example:

```text
Java Method
     |
     +--> Metadata Query A
     |       |
     |       +--> returns TABLE_NAME
     |
     +--> Metadata Query B
             |
             +--> returns COLUMN_LIST

     ↓

Dynamic SQL
     |
     +--> FROM TABLE_NAME
     +--> SELECT COLUMN_LIST
```

This should be queryable.

Example question:

```text
"How is the table name for this query determined?"
```

The agent should retrieve the metadata dependency graph and answer:

```text
The table name is not hard-coded.

It originates from:
Java method X
 -> constant SQL Y
 -> metadata query
 -> metadata table Z
 -> returned value
 -> variable T
 -> dynamic SQL Q
```

# 29. Never Hallucinate Resolution

If the analyzer cannot determine the final SQL, the answer must say:

```text
Partially resolved.
```

Example:

```text
The table name is obtained from metadata through method X.
The metadata lookup can be traced to query Y.

However, the runtime value cannot be determined statically because
the value depends on runtime input Z.
```

Never produce:

```text
The table is probably CUSTOMER_HISTORY.
```

unless evidence actually supports it.

# 31. Initial Model Strategy

Start with a strong coding-focused Qwen3-Coder-class model that fits comfortably within the 24 GB memory budget.

Benchmark at least:

```text
smaller coding model
medium ~14B coding model
```

Use quantized models where appropriate.

Do not hard-code the model name throughout the application.

Configuration:

```yaml
llm:
  provider: ollama
  model: <configured-model>
  temperature: 0.1
  context_length: <configured>
```

The exact model should remain configurable.


# 72. Evidence-Based Responses

Every technical answer should distinguish:

```text
FACT
INFERENCE
UNKNOWN
```

Example:

```text
FACT:
Method X calls Method Y.

FACT:
Method Y reads metadata table Z.

FACT:
Method Y constructs SQL dynamically.

INFERENCE:
This metadata appears to control the target table.

UNKNOWN:
The runtime value for the table cannot be determined
without the corresponding runtime metadata value.
```

This dramatically reduces hallucination.

# 87. Critical Instruction for Implementation

When implementing this project, never replace deterministic analysis with LLM guessing.

Use:

```text
Parser → facts
Graph → relationships
Resolver → deterministic resolution
Search → candidates
RAG → contextual documents
Agent → investigation/planning
LLM → reasoning/explanation
```

The LLM should be the **reasoning layer**, not the source of truth.

For unresolved dynamic SQL:

```text
return UNKNOWN
```

rather than inventing an answer.

For every important answer:

```text
claim → evidence → source location
```

should be traceable.

That is the foundation required for a local AI that can realistically behave like a technical lead over a large Java/Spark/SQL project.
